# GPU-104 — Live candidate processing service

Status: implemented on `feature/GPU-104-candidate-service`
Unit: U4
Traceability: R4–R7, R10, R16, R17; F1–F3; AE1–AE4; KTD5, KTD6, KTD9, KTD10

## Delivered

- Added `CandidateProcessingService`, a pixels-free application boundary that
  parses `track.candidate.v1`, validates timestamps and typed GPU receipt
  correlation/revisions, and maps only metadata into `DomainObservation`.
- Added one deterministic cascade state per camera/track, deterministic decision
  IDs, repository-backed replay safety, duplicate-event suppression, and
  fail-closed handling for missing/failed/mismatched GPU evidence.
- Added bounded MQTT consumer lifecycle with worker backpressure, retry limits,
  poison-message dead-lettering without copying malformed payloads, broker
  callback binding, and graceful stop behavior.
- Added candidate settings, service bootstrap, CLI `serve-candidates`, bounded
  candidate metrics, and candidate/broker readiness signals.
- Added contract and integration coverage for duplicate delivery, shadow audio,
  missing and mismatched receipts, failed evidence, malformed payloads, MQTT
  acknowledgement timing, content-fingerprint deduplication, backpressure, and
  shutdown wiring.

## Scope boundary

The service does not decode frames, access raw pixels, invoke crop Triton, or
make model-family decisions. DeepStream/native media owns those operations and
publishes typed receipts before this service receives a candidate.
